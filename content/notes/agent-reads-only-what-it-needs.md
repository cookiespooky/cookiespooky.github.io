## С чего это начинается

Пока проект маленький, агенту всё равно, как он устроен: он читает всё, и всего немного. Потом в корне появляется файл с правилами на несколько экранов, рядом — описание каждого модуля, история решений, бэклог. Агент добросовестно загружает это на каждую задачу, и счёт идёт уже не на ответ, а на чтение.

Снаружи это выглядит по-разному. Кто-то видит большой расход токенов. У кого-то бот на середине разговора теряет нить. Кто-то упирается в лимит подписки к обеду. Кто-то собрал первые автоматизации, а дальше всё начинает ломаться, и кажется, что дальше уже не его уровень. Причина у всех одна: агенту не сказано, где что лежит, и он ищет сам.

Я столкнулся с этим, когда моя рабочая папка выросла до десятка проектов и хранилища на шестьсот с лишним заметок. Дальше — то, как она устроена сейчас.

## Принцип

Агент всегда видит карту и короткие правила. Подробности подгружаются только тогда, когда работа доходит до нужного места.

Всё остальное — способы этого добиться.

## 1. Короткий корневой файл

`CLAUDE.md` (у Codex — `AGENTS.md`) в корне содержит только две вещи:

- карту папок: что где лежит и где искать подробности;
- правила, которые нельзя нарушать ни при какой задаче.

Команд сборки, описаний модулей и истории решений там нет — они ниже по дереву. Мой корневой файл — около ста строк на десяток с лишним проектов: таблица «папка — что это — куда публикуется — что читать дальше» и список того, что ломается необратимо.

## 2. Правила по папкам — с `paths:`

Правила для отдельной области лежат в `.claude/rules/<область>.md` с заголовком:

```markdown
---
paths:
  - "site/**"
---
```

Такое правило Claude Code загружает сам, и только когда агент открыл файл в этой папке. В карте корневого файла написано, какое правило к какой папке — чтобы агент мог прочитать его заранее, если планирует работу, ещё не открыв ни одного файла.

Это главный приём. Когда я разложил правила по уровням вместо того, чтобы грузить все сразу, вопрос стал стоить около 3 тысяч токенов вместо 30 тысяч — [замер](/notes/zamery-pamyati/).

## 3. Свой файл у каждой крупной папки

У папки с отдельным проектом — свой `CLAUDE.md` или `AGENTS.md`: команды, устройство, ограничения именно этого проекта. Агент читает его, только когда работает в этой папке. В корне о нём — одна строка в карте.

## 4. Документация по областям кода

Вместо одного большого README — по файлу на область: `docs/agent/<область>.md`. В файле проекта — таблица, что когда читать:

| когда | что читать |
|---|---|
| перед правкой `inbox/` | `docs/agent/core.md` |
| перед правкой `publish/` | `docs/agent/publish.md` |

У моего сайта так устроено шесть областей: контент, SEO, ассистент, скрипты страниц, сборка, деплой. Правка текста статьи не тянет за собой историю деплоя.

## 5. Команды вместо чтения файлов

Большой файл, который агент регулярно читает целиком, — кандидат на команду, которая печатает выжимку:

- не «прочитай бэклог» — у меня он больше 40 КБ, — а команда, которая печатает открытые задачи по одному тегу в двадцать строк;
- не «прочитай архив», а поиск по индексу заметок;
- не «посмотри всё новое», а одна сводка, где каждый раздел — несколько строк.

Ещё одна сторона того же: всё, что делается одинаково каждый раз, — скрипт, а не модель. Модель тратит токены на решения, а не на повторение.

## 6. Связи вместо полного обхода

Заметки и документы ссылаются друг на друга — `[[…]]` или обычными ссылками. У проекта короткая входная страница со ссылками вниз. Агент идёт по нужной ветке, а не по всем файлам подряд.

Когда агенту заранее известно, с чем связана запись, он открывает меньше: на одном из замеров такой подграф снизил расход на 26 %, а ходов стало вдвое меньше. На моём хранилище устройство записей сократило входные токены на 33–71 %, и верных ответов стало 27 из 27 вместо 21 — [замеры](/notes/zamery-pamyati/).

## 7. Проверки рядом с модулем

Проверка лежит рядом с модулем (`<имя>_check.py`) и запускается по слову: `bin/check notes` гоняет только нужное, а не весь набор. Агенту не нужно читать все тесты, чтобы проверить одну правку.

## 8. Память — индекс и факты отдельно

`MEMORY.md` — индекс, по строке на факт. Сам факт — в отдельном файле. В контексте всегда только индекс; файл подгружается, когда относится к делу.

## 9. Сначала поиск, потом чтение куска

Поиск (`grep`, `glob`), чтобы найти место, затем чтение нужных строк, а не файла целиком. Это агент делает и сам, но правило в корневом файле напоминает ему об этом на больших файлах.

## С чего начать

Порядок, в котором отдача самая большая:

1. Сократить корневой файл до карты и правил.
2. Вынести правила по папкам в `.claude/rules/` с `paths:` — основная экономия здесь.
3. Сделать команды-выжимки для файлов, которые агент читает чаще всего.

На подписке Claude Code разница видна не в долларах, а в лимитах: те же задачи реже упираются в потолок.

## Инструкция для агента целиком

Её можно отдать своему агенту как есть — он разберёт проект и предложит, что куда вынести:

```markdown
Задача: устроить проект так, чтобы на каждую задачу читалось только нужное.

Принцип: агент всегда видит карту и короткие правила; подробности подгружаются,
только когда работа доходит до нужного места.

1. Корневой CLAUDE.md (для Codex — AGENTS.md): только карта папок (что где лежит,
   где искать подробности) и правила, которые нельзя нарушать. Команды сборки,
   описания модулей и историю решений — ниже по дереву.
2. Правила отдельных областей — в .claude/rules/<область>.md с заголовком
   paths: ["<папка>/**"]; в карте корневого файла — какое правило к какой папке.
3. У папки с отдельным проектом — свой CLAUDE.md или AGENTS.md: команды,
   устройство, ограничения.
4. Вместо одного большого README — docs/agent/<область>.md и таблица
   «перед правкой X читать Y» в файле проекта.
5. Большие файлы, которые читаются целиком регулярно, — заменить командами,
   которые печатают выжимку (задачи по тегу, поиск по индексу, сводка).
6. Связи между заметками и короткая входная страница проекта со ссылками вниз —
   идти по нужной ветке, а не по всем файлам.
7. Проверки — рядом с модулем, запуск по слову, а не весь набор.
8. Память: MEMORY.md — индекс по строке на факт, факты — отдельными файлами.
9. Сначала поиск, потом чтение нужных строк, а не файла целиком.

Начни с разбора: какие файлы сейчас читаются на каждую задачу, сколько в них
строк, что из этого нужно не всегда. Предложи план по шагам 1–3 и ничего
не удаляй — только переноси, и в старом месте оставляй ссылку.
```

## Оговорки

- Цифры — из замеров на моих проектах и одной модели; на чужом проекте они будут другими, и это стоит померить у себя: стоимость и входные токены видны в итоге каждого запуска.
- Структура не заменяет хорошую постановку задачи: если в просьбе не сказано, о какой части проекта речь, агент всё равно пойдёт искать.
