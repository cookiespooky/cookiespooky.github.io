# SEO-завод

Конвейер: спрос → кластеры → статьи в `content/blog/` → лиды на `/services/`.
Позже выносится в отдельный продукт, поэтому граница жёсткая: завод **только пишет markdown в
`content/`** и ничего не знает про внутренности notepub.

## Главная идея

Продукт здесь — не генератор текста, его повторит кто угодно. Продукт — **реестр**
(`clusters.yaml`): база «кластер → URL → статус → факт позиций». Именно он не даёт написать вторую
статью под тот же интент и позволяет решать, что расширять. Всё остальное вокруг него.

Правило, которое нельзя нарушать: **один кластер = один URL**.

## Почему информационный хвост, а не «заказать разработку»

Коммерческий топ Яндекса по головным запросам занят агрегаторами, студиями с большим ссылочным и
рекламой, и на коммерческих запросах Яндекс сильно взвешивает коммерческие факторы: цены, отзывы,
реквизиты, регион, ассортимент. Контентом в эту выдачу не входят.

Информационная выдача всё ещё вознаграждает предметность, и практик с 34 реальными кейсами имеет там
настоящее преимущество. Плюс информационный трафик накапливает поведенческие сигналы хоста, которые
потом делают коммерческие страницы вообще ранжируемыми.

Отсюда порядок: **информационный хвост в блог → рост доверия хоста → коммерческий длинный хвост на
`/services/`**. Не путать между собой: «заказать телеграм бота для записи клиентов» —
низкочастотный *коммерческий* запрос, он идёт на лендинг услуги. «Сколько стоит сделать телеграм
бота» — то же поле, другой интент, идёт в блог.

## Wordstat API: как он на самом деле устроен

Проверено по документации, потому что путь через API Директа — устаревший. Актуальный Wordstat API
живёт в **Yandex Cloud / AI Studio Search API**, а не в Директе:

```
POST https://searchapi.api.cloud.yandex.net/v2/wordstat/topRequests
Authorization: Bearer <IAM-токен>
```

Аутентификация — обычный сервисный аккаунт Yandex Cloud с ролью `search-api.webSearch.user`.
Сервисный аккаунт и креды в CI уже есть — теми же деплоятся функции в `lab/`.

Методы: `GetTop` (топ запросов с этими словами за 30 дней), `GetDynamics` (частота по месяцам,
неделям, дням), `GetRegionsDistribution` (распределение по регионам), `GetRegionsTree` (коды
регионов, не тарифицируется).

Запрос `GetTop`: `phrase` (до 400 символов), `numPhrases` (1–2000), `regions` (до 100 id),
`devices` (`DEVICE_ALL` / `DESKTOP` / `PHONE` / `TABLET`, до 3), `folderId`.
Ответ: `totalCount`, `results[] {phrase, count}`, `associations[]` — похожие запросы.

**Цена:** 20 ₽ за 1000 запросов для `GetTop` и `GetDynamics`, 50 ₽ за 1000 для
`GetRegionsDistribution`. Бесплатного объёма у Search API нет — нужен платёжный аккаунт Yandex Cloud
с положительным балансом. Это первый по-настоящему платный сервис здесь: бесплатный тариф Cloud
Functions, на котором живут функции в `lab/`, к Search API не относится.

**Настоящее ограничение — не деньги, а квота: `GetTop` разрешает 10 запросов в секунду, но только
100 запросов в час.** Поэтому сборщик обязан быть с ограничителем скорости и возобновляемым: упасть
на 80-м запросе и начать сначала будет стоить часа ожидания.

Прочие неизменяемые лимиты: длина запроса 400 символов, до 40 слов. В справке по лимитам указан
максимум 250 результатов, тогда как `numPhrases` в описании метода допускает до 2000 — расхождение,
проверить эмпирически.

### Бюджет первой волны

| Что | Запросов | Стоимость |
|---|---|---|
| `GetTop` по сидам | ~50 | 1 ₽ |
| `GetDynamics` на выживших кластерах | ~13 | 0,3 ₽ |
| `GetRegionsTree` | 1 | 0 ₽ |
| Выдача для конкуренции, отложенные ночные | ~40 | 1 ₽ |

Порядка трёх рублей. Даже на порядок более широкая программа — 1000 запросов Wordstat плюс 1000
отложенных запросов выдачи — это около 50 ₽. Пополнять баланс надо, но сумма символическая.

### Выдача: отложенные вместо синхронных

Оценка конкуренции требует топов, а это уже другая цена. Разница принципиальная:

| Тип запроса | Цена за 1000 |
|---|---|
| Дневные синхронные | 488 ₽ |
| Ночные синхронные | 366 ₽ |
| Дневные отложенные | 30,5 ₽ |
| **Ночные отложенные** | **25,41 ₽** |

Отложенные дешевле синхронных в 16 раз. Реальное время для анализа конкуренции не нужно совсем,
поэтому топы забираем **только отложенными и ночью**. Синхронные запросы к выдаче в этом контуре —
ошибка на порядок в счёте.

### Бесплатная альтернатива на первую волну

Веб-интерфейс `wordstat.yandex.ru` бесплатен и, в отличие от API, **поддерживает операторы**. Для 13
кластеров и 46 сидов это пара часов ручной работы и ноль рублей, причём с операторной точностью,
которой у API нет.

Формат реестра одинаково принимает и ручные числа, и ответ API. Ценность API — не в данных, а в
автоматизации и повторяемости; она начинает окупаться, когда завод становится продуктом и волн
становится много. На первой волне это вопрос вашего времени против пополнения баланса, а не
качества данных.

### Из чего берётся частота

Операторы Wordstat (`"фраза"`, `"!фраза"`, `[порядок]`, `+стоп-слово`) в документации API **не
описаны**, поэтому метод на них не опирается. Работать нужно по факту ответа:

- `totalCount` — сколько всего запросов содержат эти слова. Это широкий потолок, приоритизировать по
  нему нельзя, ровно та же ошибка, что и с широким соответствием в веб-интерфейсе.
- `results[].count` — частота **конкретной формулировки**, как её реально набирают люди. Вот по
  этому и приоритизируем.

Это лучше операторной арифметики: вместо оценки вы получаете фактическое распределение реальных
запросов. И меняет тактику сбора — **один `GetTop` с большим `numPhrases` разворачивает целый
кластер**, до 2000 фраз со своими частотами плюс ассоциации. Поэтому сид-фраз должно быть мало и они
должны быть удачными, а не «одна фраза — один запрос к API».

Если операторы в поле `phrase` всё же сработают — это бонус, проверять эмпирически, но метод от них
не зависит.

### Доступ

Русская и английская версии документации расходятся. Английская описывает четыре шага, включая форму
заявки и обращение в поддержку Директа с логином и `ClientId`. Русская говорит, что всё переехало в
Search API Yandex Cloud, где доступ — это роль на сервисном аккаунте.

Быстрее всего разрешается практикой: выдать сервисному аккаунту роль `search-api.webSearch.user`,
взять IAM-токен и сделать один запрос. Если ответ пришёл — никакая заявка не нужна. OAuth-приложение
с `verification_code` при облачном пути не участвует вообще.

## Параметры приоритизации

| Параметр | Что решает | Источник |
|---|---|---|
| `count` | частота конкретной формулировки | `results[].count` в `GetTop` |
| `intent` | статья или лендинг | слова-маркеры + состав выдачи |
| `competition` | можно ли вообще войти | топ-10: сколько агрегаторов, есть ли мелкие сайты |
| `money_distance` | конвертит ли трафик | вручную, 1–5 |
| `cases` | есть ли что сказать своё | 34 кейса в `content/cases/` |
| сезонность | порядок публикации | `GetDynamics` |

Приоритет ≈ `count × intent × покрытие кейсом ÷ competition`.

`money_distance` — **жёсткий фильтр, а не слагаемое**: всё, что дальше 3, не пишется вообще. Именно
этот параметр обычно игнорируют, и поэтому заводы дают трафик, который не конвертит.

Маркеры интента: `как`, `почему`, `что такое`, `чем отличается`, `сколько стоит` → информационный;
`заказать`, `цена`, `стоимость`, `услуги`, `под ключ`, `разработка` → коммерческий.

## Гейт качества

Массовая генерация без подложки Яндексом отфильтровывается — на этом же сайте уже лежали 200 тонких
страниц с медианой 634 символа и нулевым трафиком, это проверено на практике.

Поэтому в статье обязано быть то, чего нет ни у кого другого: цифры из кейса, код, скриншот, разбор
своей ошибки. Каждая статья ссылается на конкретный кейс через `related` — это и E-E-A-T, и то, что
отличает завод от генератора шлака. **Кластер без кейса не пишется**, а ставится в очередь на «сначала
сделать, потом написать».

## Можно ли писать до Вордстата

Да, если понимать, где именно теряется, а где нет.

**Переписывание текста по тому же адресу не стоит почти ничего.** Обновление контента — штатный жизненный цикл
страницы, за него не наказывают. Единственная цена — инерция переоценки: Яндекс пересчитывает текстовую
релевантность не мгновенно, и после переработки новая версия может неделями ранжироваться по старой оценке.
То есть вы не теряете накопленное, вы ждёте.

**Теряется в трёх других местах:**

- **Смена URL.** Если ресёрч покажет другой кластер, захочется поменять слаг. Старый адрес умирает, новый
  начинает с нуля, а настоящего 301 на GitHub Pages нет. Сейчас накоплений ноль, поэтому смена бесплатна;
  через полгода — нет.
- **Каннибализация.** Десять статей «по наитию» почти наверняка перекроют друг другу интент, а слияние — это
  снова удаление URL.
- **Хостовые сигналы.** Яндекс оценивает сайт целиком, и пачка малополезных страниц какое-то время висит на
  хосте даже после починки. Это главный аргумент против «напишем много, разберёмся позже».

**Отсюда политика.** Писать до замеров можно при трёх условиях:

1. Две-четыре статьи, не десять. Малое количество физически не создаёт каннибализации, а для проверки формата
   даёт столько же информации.
2. Слаг на уровне темы, а не запроса: `/blog/stranicy-pod-goroda/` переживёт перенацеливание, а
   `/blog/kak-sdelat-stranicy-usluga-gorod-dlya-seo/` придётся менять.
3. Сразу в реестр со `stage: written` и занятым `target_url` — это и есть механизм против второй статьи под
   тот же интент.

Брать те кластеры, которые не исчезнут из плана ни при каком результате замеров: `service-city-pages` (кейс
`gorod-katalog` буквально про «10 услуг × 15 городов») и `form-without-backend` (его решают три кейса подряд).
Частота уточнит приоритет, но не отменит тему.

**Побочная выгода.** Опубликованные статьи дают то, чего Вордстат не даёт: Вебмастер покажет, по каким
запросам страницы реально получают показы. Это факт по вашему сайту, а не оценка рынка, — то есть две-три
статьи, простоявшие месяц, работают входными данными для ресёрча, а не помехой ему.

**Но порядок важнее всего остального: публиковать только после переезда на домен.** Иначе статьи
проиндексируются на `github.io` и потом сменят адрес — ровно та потеря, которой всё это избегает. Писать можно
начинать сейчас, публиковать — после HTTPS и Вебмастера. См. «Deployment state» в `CLAUDE.md`.

## Состояние: чего ещё нет

Шаг 0 — **измеримость**, а не Wordstat. Без обратной связи это не завод, а свалка контента: писать
можно, понять что сработало — нельзя.

- [x] Метрика: счётчик `108674124` подключён в `config.yaml`. Его история описывает URL, которых больше нет,
      поэтому для решений о контенте смотреть данные с даты релиза
- [x] Метатег Вебмастера (`74ea07470235e3be`) в сборке. Само подтверждение пройдёт только после деплоя:
      сейчас домен отдаёт старую версию сайта, где тега нет
- [ ] Яндекс.Вебмастер: подтвердить домен после пуша. Даёт бесплатно реальные запросы и показы — точнее,
      чем оценки Wordstat, потому что это факт по вашему сайту
- [ ] Wordstat API: путь облачный, бесплатного объёма нет. Выдать сервисному аккаунту роль
      `search-api.webSearch.user`, пополнить баланс и проверить одним запросом, нужна ли заявка.
      Либо пропустить и собрать первую волну руками через веб-Wordstat
- [ ] Оценка конкуренции: нужна выдача. Бесплатный путь — Yandex XML, но его квота привязана к сайту,
      подтверждённому в Вебмастере, то есть зависит от пункта выше
- [ ] Теги у кейсов: поле пустое у всех 34, а это вход для будущей таксономии

Источник ключей всё равно держим сменным интерфейсом: облачный Search API — платный сервис с
квотами, и полезно иметь возможность подставить бесплатные источники (подсказки Яндекса, «вместе с
этим искали», данные Вебмастера).

Отдельно, на будущее как продукта: условия использования ограничивают хранение и перепродажу данных
Wordstat. Если завод станет SaaS — смотреть это до первых клиентов, а не после.

## Что сейчас в реестре

13 кластеров, 46 сид-фраз, все со стадией `seed` — то есть фразы выписаны из портфолио, но частоты не
собраны. Сиды здесь — это входы для `GetTop`, а не финальный список ключей: реальные формулировки
придут из ответа. Два направления, выбранные по марже: сайты и каталоги на статике, боты и мини-приложения.

Первая на проверку — гипотеза `markdown-notes-to-site`: живой спрос, конкуренция почти не
коммерческая, под темой четыре кейса и свой движок. Похоже на самый дешёвый вход, но это гипотеза, её
надо подтвердить частотой и выдачей.
